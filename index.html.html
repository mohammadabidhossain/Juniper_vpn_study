PHASE 1 — VPN FUNDAMENTALS

1.1 — What is a VPN, Really?

Most people say "VPN = privacy." That's superficial. Let's be precise.
A VPN is a logical private network constructed over a shared public infrastructure, using encapsulation, encryption, and authentication to make geographically separated private networks behave as if they are directly connected.

Three core pillars:

┌─────────────────────────────────────────────────────────────┐
│                    VPN = 3 PILLARS                          │
│                                                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │ENCAPSULATION│  │ ENCRYPTION  │  │   AUTHENTICATION    │  │
│  │             │  │             │  │                     │  │
│  │ Wrapping    │  │ Making data │  │ Proving identity    │  │
│  │ private     │  │ unreadable  │  │ of both endpoints   │  │
│  │ packets     │  │ to others   │  │ before tunnel opens │  │
│  │ inside      │  │             │  │                     │  │
│  │ public      │  │             │  │                     │  │
│  │ packets     │  │             │  │                     │  │
│  └─────────────┘  └─────────────┘  └─────────────────────┘  │
│                                                             │
│  WITHOUT ALL THREE, YOU DO NOT HAVE A PROPER VPN            │
└─────────────────────────────────────────────────────────────┘

Real-world analogy:
Imagine you need to send classified bank documents from Rajshahi to Dhaka. You cannot use a private courier road — only public highways exist.

  • Encapsulation = You put the classified document inside a sealed unmarked box. The box has delivery addresses on the outside, but nobody can see what's inside.
  • Encryption = The document inside uses a cipher — even if someone breaks open the box, they read gibberish.
  • Authentication = The recipient must show ID before the box is handed over. You verify the recipient is actually who they claim to be.

The public highway is the Internet. The sealed, encrypted box is your VPN tunnel.

1.3 — The Private IP Problem: Why 10.x.x.x Cannot Cross the Internet

This is the most critical fundamental to understand deeply.
The Internet routing system only routes PUBLIC IP addresses. Here's why:

┌─────────────────────────────────────────────────────────────────┐
│                    IP ADDRESS UNIVERSE                          │
│                                                                 │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │                    PUBLIC IP SPACE                        │  │
│  │  (4,294,967,296 total addresses - private ranges)         │  │
│  │                                                           │  │
│  │  Examples: 203.0.113.1, 8.8.8.8, 198.51.100.1             │  │
│  │  Owned by: ISPs, companies, governments                   │  │
│  │  Routable: YES — Internet backbone knows how to           │  │
│  │            find these addresses                           │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                 │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │                 PRIVATE IP RANGES (RFC 1918)              │  │
│  │                                                           │  │
│  │  10.0.0.0/8    → 10.0.0.0   – 10.255.255.255              │  │
│  │  172.16.0.0/12 → 172.16.0.0 – 172.31.255.255              │  │
│  │  192.168.0.0/16→ 192.168.0.0– 192.168.255.255             │  │
│  │                                                           │  │
│  │  Owned by: Nobody — everyone uses them internally         │  │
│  │  Routable on Internet: NO — Internet routers DROP them    │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘

WHY are private IPs not routable on the Internet?
Because private IP ranges are used by MILLIONS of organizations simultaneously. Consider:

  RAKUB Rajshahi Office:       10.10.10.0/24
  Grameen Bank Dhaka:          10.10.10.0/24
  A factory in Chittagong:     10.10.10.0/24
  A school in Sylhet:          10.10.10.0/24
  
  ALL FOUR use IDENTICAL address ranges!

If an Internet router received a packet destined for 10.10.10.100, it would have no idea which organization's network to send it to. The address is ambiguous globally — it only has meaning within a specific private network.
This is why Internet backbone routers are configured to drop all RFC 1918 traffic by default.

1.4 — Public IP, ISP Role, and How Internet Routing Works

Let's trace how public IP routing actually works:

  Institution A                 Internet Backbone                Institution B
  ─────────────                 ─────────────────                ─────────────
  
  PC: 10.10.10.100             [ISP-A Router]
         │                            │
         │                     Routes based on
  [Juniper Router]             BGP routing table
  Public IP: 203.0.113.1              │
         │                    [ISP Core Router 1]
         │                            │
         └────────────────────[ISP Core Router 2]────────────────[Juniper Router]
                                      │                          Public: 198.51.100.1
                                 Routes based                              │
                                 on BGP only                    [Institution B LAN]

BGP (Border Gateway Protocol) is the routing protocol of the Internet. Every ISP advertises which public IP blocks they own. For example:
ISP-A tells the world: "I own 203.0.113.0/24 — send traffic here"
ISP-B tells the world: "I own 198.51.100.0/24 — send traffic here"

1.5 — NAT: The Partial Solution (And Why It's Not Enough)

WITHOUT NAT:
  PC (10.10.10.100) → sends packet to Google (8.8.8.8)
  Source IP: 10.10.10.100 ← Internet routers DROP this (private source)
  
WITH NAT:
  PC (10.10.10.100) → Router translates → Source becomes 203.0.113.1
  Source IP: 203.0.113.1 → Internet routers ACCEPT this (public source)
  
  NAT Table on Router:
  ┌─────────────────────────────────────────────────────┐
  │ Inside Local      │ Inside Global    │ Destination  │
  │ 10.10.10.100:1234 │ 203.0.113.1:5001 │ 8.8.8.8:443  │
  └─────────────────────────────────────────────────────┘

Problem Scenario:
  Institution A PC (10.10.10.100) wants to reach Institution B PC (10.20.20.100)
  
  With NAT:
  Step 1: PC-A sends packet → Destination: 10.20.20.100
  Step 2: Router-A looks at routing table → No route to 10.20.20.100 (private!)
  Step 3: Router-A cannot NAT this — WHERE would it send it on the public Internet?
  
  The Internet has NO idea where 10.20.20.0/24 lives!
  There is no ISP announcing this range!
  NAT cannot solve the two-private-network problem.

STEP 2: ARP Resolution

ARP REQUEST (Broadcast):
═══════════════════════
  [PC-A] ──────────────────────────────► [Everyone on LAN]
  
  Ethernet Frame:
  ┌─────────────────────────────────────────────────────────────┐
  │ Dst MAC: FF:FF:FF:FF:FF:FF (Broadcast)                      │
  │ Src MAC: AA:BB:CC:DD:EE:01 (PC-A's MAC)                     │
  │ Type: ARP (0x0806)                                          │
  │                                                             │
  │ ARP Payload:                                                │
  │   Operation: REQUEST (1)                                    │
  │   Sender IP:  10.10.10.100                                  │
  │   Sender MAC: AA:BB:CC:DD:EE:01                             │
  │   Target IP:  10.10.10.1  ← Who has this IP? Tell me!      │
  │   Target MAC: 00:00:00:00:00:00 (unknown)                   │
  └─────────────────────────────────────────────────────────────┘

ARP REPLY (Unicast):
════════════════════
  [Router-A] ──────────────────────────────► [PC-A]
  
  ┌─────────────────────────────────────────────────────────────┐
  │ Dst MAC: AA:BB:CC:DD:EE:01 (PC-A)                           │
  │ Src MAC: FF:EE:DD:CC:BB:01 (Router-A's LAN interface MAC)   │
  │ Type: ARP (0x0806)                                          │
  │                                                             │
  │ ARP Payload:                                                │
  │   Operation: REPLY (2)                                      │
  │   Sender IP:  10.10.10.1                                    │
  │   Sender MAC: FF:EE:DD:CC:BB:01  ← Here I am!              │
  │   Target IP:  10.10.10.100                                  │
  │   Target MAC: AA:BB:CC:DD:EE:01                             │
  └─────────────────────────────────────────────────────────────┘
  
  PC-A now knows: "To reach 10.10.10.1, use MAC FF:EE:DD:CC:BB:01"
  PC-A updates its ARP cache.

PHASE 3 — VPN TECHNOLOGY COMPARISON

3.1 — All VPN Types Explained

Site-to-Site VPN
  [Branch LAN] ──[VPN Router]══════ Internet ══════[VPN Router]──[HQ LAN]
  Purpose: Connect two FIXED locations permanently

Remote Access VPN
  [Employee Laptop] ══════ Internet ══════[VPN Gateway]──[Corporate LAN]
  Purpose: Individual users accessing corporate network remotely

MPLS VPN (L3VPN)
  [Branch A] ──[PE Router]──[MPLS Cloud (ISP)]──[PE Router]──[Branch B]
  Purpose: ISP-managed private WAN

GRE Tunnel
  [Router A] ══════════════[Router B]
  Purpose: Encapsulation only — creates logical point-to-point link

IPsec Tunnel
  [Router A] ══════════════[Router B]
  Purpose: Secure encapsulation with encryption

SSL VPN
  [Browser/Client] ──HTTPS──[SSL VPN Gateway]──[Internal Resources]
  Purpose: Web-based remote access, no client software needed

DMVPN (Dynamic Multipoint VPN)
  Purpose: Hub-and-spoke with dynamic spoke-to-spoke tunnels

SD-WAN
  Purpose: Software-defined routing across multiple WAN links

8.1 — Complete JunOS Configuration: Institution A (SRX-A)

## ══════════════════════════════════════════════════════════
## JUNIPER SRX-A COMPLETE IPsec SITE-TO-SITE VPN CONFIG
## Institution A: LAN 10.10.10.0/24, WAN 203.0.113.1
## Remote Institution B: LAN 10.20.20.0/24, WAN 198.51.100.1
## ══════════════════════════════════════════════════════════

interfaces {
    ge-0/0/0 {
        unit 0 { family inet { address 10.10.10.1/24; } }
    }
    ge-0/0/1 {
        unit 0 { family inet { address 203.0.113.1/30; } }
    }
    st0 {
        unit 0 { family inet { address 172.16.0.1/30; } }
    }
}

routing-options {
    static {
        route 0.0.0.0/0 next-hop 203.0.113.254;
        route 10.20.20.0/24 next-hop st0.0;
    }
}

security {
    zones {
        security-zone trust {
            interfaces {
                ge-0/0/0.0 { host-inbound-traffic { system-services { ping; ssh; dhcp; } } }
            }
            address-book { address local-net 10.10.10.0/24; }
        }
        
        security-zone untrust {
            interfaces {
                ge-0/0/1.0 { host-inbound-traffic { system-services { ike; } } }
            }
            address-book { address remote-gw 198.51.100.1/32; }
        }
        
        security-zone vpn {
            interfaces { st0.0; }
            address-book { address remote-net 10.20.20.0/24; }
        }
    }

    ike {
        proposal phase1-proposal {
            authentication-method pre-shared-keys;
            dh-group group14;
            authentication-algorithm sha-256;
            encryption-algorithm aes-256-cbc;
            lifetime-seconds 86400;
        }
        
        policy ike-policy-to-b {
            mode main;
            proposals phase1-proposal;
            pre-shared-key ascii-text "R@KUBVPNS3cr3t!2024";
        }
        
        gateway vpn-gateway-to-b {
            ike-policy ike-policy-to-b;
            address 198.51.100.1;
            dead-peer-detection { interval 10; threshold 5; }
            external-interface ge-0/0/1.0;
            version v2-only;
            local-identity inet 203.0.113.1;
            remote-identity inet 198.51.100.1;
        }
    }

    ipsec {
        proposal phase2-proposal {
            protocol esp;
            authentication-algorithm hmac-sha-256-128;
            encryption-algorithm aes-256-cbc;
            lifetime-seconds 3600;
        }
        
        policy ipsec-policy {
            perfect-forward-secrecy { keys group14; }
            proposals phase2-proposal;
        }
        
        vpn site-b-vpn {
            bind-interface st0.0;
            ike {
                gateway vpn-gateway-to-b;
                ipsec-policy ipsec-policy;
            }
            traffic-selector ts-a-to-b {
                local-ip 0.0.0.0/0;
                remote-ip 0.0.0.0/0;
            }
            establish-tunnels immediately;
        }
    }

    policies {
        from-zone trust to-zone vpn {
            policy trust-to-vpn {
                match {
                    source-address local-net;
                    destination-address remote-net;
                    application any;
                }
                then { permit; }
            }
        }
        
        from-zone vpn to-zone trust {
            policy vpn-to-trust {
                match {
                    source-address remote-net;
                    destination-address local-net;
                    application any;
                }
                then { permit; }
            }
        }
        
        from-zone trust to-zone untrust {
            policy trust-to-internet {
                match {
                    source-address local-net;
                    destination-address any;
                    application any;
                }
                then { permit; }
            }
        }
    }

    nat {
        source {
            rule-set trust-to-internet {
                from zone trust;
                to zone untrust;
                rule nat-rule {
                    match {
                        source-address 10.10.10.0/24;
                        destination-address 0.0.0.0/0;
                    }
                    then { source-nat { interface; } }
                }
            }
        }
    }
}

9.2 — Scenario: Phase 1 Fails (IKE SA Not Coming Up)

SYMPTOMS:

  • show security ike sa → empty or state DOWN
  • show log messages → "NO_PROPOSAL_CHOSEN" or "AUTHENTICATION_FAILED"
Error: "NO_PROPOSAL_CHOSEN"
┌──────────────────────────────────────────────────────────────┐
│ Cause: Algorithm mismatch between peers                      │
│ Fix: Compare proposals on BOTH sides:                        │
│ Solution: Make proposals IDENTICAL on both peers             │
└──────────────────────────────────────────────────────────────┘

Error: "AUTHENTICATION_FAILED" 
┌──────────────────────────────────────────────────────────────┐
│ Cause: PSK mismatch                                          │
│ Fix: Verify PSK on both sides — case sensitive!              │
└──────────────────────────────────────────────────────────────┘
9.3 — Scenario: Phase 2 Fails (IPsec SA Not Coming Up)

SYMPTOMS:

  • IKE SA is UP
  • show security ipsec sa → empty or no entries
Error: "TS_UNACCEPTABLE" (Traffic Selector mismatch)
┌──────────────────────────────────────────────────────────────┐
│ Cause: Traffic selectors (proxy IDs) don't match             │
│ Fix for route-based VPN with 0.0.0.0/0 selectors:            │
│ vpn site-b-vpn {                                             │
│   traffic-selector ts-a-to-b {                               │
│     local-ip 0.0.0.0/0;                                      │
│     remote-ip 0.0.0.0/0;                                     │
│   }                                                          │
│ }                                                            │
└──────────────────────────────────────────────────────────────┘
9.4 — Scenario: Tunnel UP but No Traffic

SYMPTOMS: Both IKE SA and IPsec SA show UP. Ping from SRX itself works, but from LAN host fails.

ping 10.20.20.100 routing-instance default            ## From SRX router
ping 10.20.20.100 source 10.10.10.1 routing-instance default  ## From LAN IP

If #1 works but #2 fails → Security policy issue. If both fail → Routing issue.
